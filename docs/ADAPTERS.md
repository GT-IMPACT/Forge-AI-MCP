# Адаптеры рецептов

## Реестры Minecraft и владелец регистрации

`minecraft` читает CraftingManager/FurnaceRecipes всех модов. Карты: crafting-shaped,
crafting-shapeless, furnace, crafting-custom. Поддержаны точные классы ShapedRecipes,
ShapelessRecipes, ShapedOreRecipe, ShapelessOreRecipe; другие IRecipe/подклассы остаются
частичными и не импортируются как обычный редактируемый рецепт. grid содержит width/height,
cells (индексы itemInputs или null), mirrored. Повторный ингредиент — отдельный слот.
Плавка содержит experience (текущее значение runtime lookup), стандартные 200 тиков;
топливо и контейнеры не являются дополнительными выходами этой записи.

`RecipeAdapter.craftingRegistration(environment)` позволяет проверенному форку владеть
регистрацией этих рецептов. Контекст возвращается как list_adapters.craftingRegistration
и registration в ответах адаптера minecraft. GT Impact проверяет наличие сигнатур
GT_ModHandler shaped/shapeless/smelting и направляет ИИ к своему скиллу.
Если GregTech установлен, но профиль неизвестен/неоднозначен, требует проверить API форка,
не допускает молчаливого выбора GameRegistry. Это инструкции/данные для ИИ, без генератора кода.

Черновики поддерживают kind shaped/shapeless/furnace, grid, copiesInputNbt и experience.
Структурная проверка grid гарантирует размеры 1..3, пустые клетки и однозначное размещение
каждого входного слота. Неполные черновики сохраняются; игровую логику проверяет ИИ по скиллу.

`RecipeAdapter` — Kotlin-интерфейс: уникальный `id`, `detect(environment)` и `call(operation, arguments, environment, codec)`.
`AdapterRegistry` хранит провайдеры, проверяет совместимость и направляет запрос только в явно выбранный адаптер. Внешний мод может зарегистрировать провайдер при init через `RecipeAdapters.register(provider)`.

Каждый форк получает отдельный ID, проверку признаков и руководство. Mod ID `gregtech` недостаточен для выбора. Встроенный `gregtech-impact` проверяет namespace Impact, специальные карты и форму API; неизвестный или несовместимый GT не активируется. Проверка совместимости не доказывает точный коммит JAR. `provenance` разделяет sourceProfileCommit и сведения установленного мода.

Общий MCP-контракт:

| Операция | Назначение |
| --- | --- |
| list_adapters | Доступность и причины отказа |
| list_recipe_maps | Карты конкретного адаптера |
| search_machine_recipes | Поиск с фильтрами и пагинацией |
| get_machine_recipe | Детали ранее найденного рецепта |
| get_recipe_authoring_guide | Скилл и API конкретного профиля |

Вызовы адаптера требуют `adapter`. Руководство можно читать без установленного мода: `runtimeAvailable` показывает доступность игровых данных. Новый провайдер реализует эти операции; неизвестные операции должны возвращать ошибку. Новые специализированные операции также нужно объявить в каталоге stdio-моста и ClientTools.

### Представление карт в NEI

Runtime-реестр дополнительно обогащает `list_recipe_maps.results[].presentation` через `NeiPresentation`.
Это необязательные данные интерфейса: `name`, `handler`, `overlay`, `mod` и `icon`.
`icon.kind=item` содержит `stack`, `kind=handler` — `handler/overlay` текстурного значка,
`kind=text` — первые две буквы имени в `text`. Порядок выбора совпадает с NEI: изображение, предмет, текст.
Для получения метаданных используется `GuiRecipeTab.getHandlerInfo`; PNG текстурного значка создаётся через очередь RenderTick,
а не на HTTP-потоке. Пара `handler/overlay` входит в ключ кэша значка.

GT Impact привязывает хандлер к точному экземпляру его карты (включая карты и хандлеры аддонов).
Если прямой связи нет, допускается только единственный зарегистрированный хандлер с точным overlay карты.
Minecraft использует свои штатные shaped/shapeless/furnace хандлеры.
Новые адаптеры могут объявить в данных карты `neiHandler` и `neiOverlay` для явной привязки.
Отсутствующая привязка не меняет доступность рецептов; интерфейс использует имя карты и текстовый значок.
Представление карты не включается в идентичность native-рецепта.

`get_recipes` / `get_usages` возвращают те же данные `presentation` у каждого результата NEI.
Хандлеры различаются по паре handler ID / overlay ID: одинаковый класс может обслуживать несколько карт.

GT подключается через reflection после detection: обязательной GT зависимости нет. ForgeMCP не загружает отсутствующие классы GT из собственного bytecode. Native ItemStack/FluidStack преобразуются codec на клиентском потоке игры. Адаптеры не должны изменять коллекции, стеки и состояние игры.

Модель различает machine и assembly-line, сохраняет входы/выходы, жидкости, NBT, шансы, флаги, энергию, special items/value, исследования и альтернативы. Дополнительные public поля попадают в extensions; непрозрачные значения дают warnings и complete=false. Динамические findRecipe результаты не перечисляются.

ID состоит из adapter/map/хеша данных. Порядок списка рецептов не участвует в хеше; локализованные имена и provenance исключены. SNBT сравнивается как строка. Одинаковое экспортируемое содержимое получает одинаковый ID; это не уникальный адрес Java-объекта. Кэш ограничен 4096 обнаруженными рецептами; чтение проверяет наличие объекта и неизменность содержимого. После смены сессии или изменения коллекции нужен повторный поиск.

Скиллы лежат в ресурсах assets/forgeaimcp/mcp/skills и автоматически распаковываются в forgemcp/skills. Их также отдаёт get_recipe_authoring_guide, поэтому ИИ может прочитать инструкции без глобальной установки скилла. Упаковку нового скилла нужно добавить в McpInstallation. Генерации и применения Kotlin-кода через MCP нет: ИИ пишет код самостоятельно по руководству и runtime данным.

Визуальный редактор — отдельный loopback HTTP-сервер EditorServer на webPort. Он запускается командой ui, использует те же ClientTools через клиентский поток и сохраняет пользовательские данные через DraftStore. Получение PNG ставит задачи в очередь ItemIcons; только RenderTick END выполняет GL-рендер, чтение пикселей и пакетный экспорт. Каталог NDJSON сохраняет записи и при ошибках иконок, с iconError/detailsError; состояние экспорта сообщает неполноту. Кэш PNG учитывает Item ID, metadata, NBT и профиль модов/ресурспаков. HTTP принимает только свой Host; POST требует собственный заголовок и проверяет Origin.

Черновик schemaVersion=1 содержит id/title, adapter/map/kind, itemInputs/itemOutputs, fluidInputs/fluidOutputs, specialItems, durationTicks/eut/specialValue, research и notes. Слот предмета имеет item/metadata/count/nbt, выход — chance (шкала 10000), вход может иметь oreDictionary или alternatives. Жидкость имеет fluid/amount/nbt (mB). При импорте native рецепта sourceRecipeId/source сохраняют контекст и неподдерживаемые поля. Структурная проверка при сохранении не выполняет рецептурную логику GT. MCP list_recipe_drafts/get_recipe_draft читает данные даже без открытого HTTP-редактора; tools остаются read-only.
